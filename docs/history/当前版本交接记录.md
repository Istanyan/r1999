## 二、自己跑测试的方法

### 方法 1：GUI（推荐，和历史上 5a/7/7b 的测试条件一致）

```
python -X utf8 gui.py
```

GUI 里走位模式默认 **hybrid**。选 r1999，设置局数，开始。

### 方法 2：命令行严格运行器（会强制校验版本和走位模式）

```
python -X utf8 temp\_run_round_strict.py <标签> <局数> <模式>
```

例：

```
python -X utf8 temp\_run_round_strict.py M1 5 hybrid
```

它会：
1. 必须显式传走位模式，不依赖代码默认值
2. 日志头写入版本 sha1 + 行数
3. 启动后回读日志确认模式，不符就作废数据
4. 输出严格去重统计（避免 Tee 重复计数）

### 方法 3：直接命令行（**注意坑**）

`main.py` 命令行的走位模式默认是 **`strafe`**，与 GUI 的 `hybrid` 不同。
之前五轮测试就是因为这个，全部跑成了 strafe，导致与 7b 不可比。

如要用命令行，必须显式设：

```powershell
$env:R1999_NO_DANGER_MODE='hybrid'
$env:R1999_MAX_RUNS='5'
python -X utf8 -c "import sys; sys.path.insert(0,'.'); from games.r1999.r1999 import Loop; Loop().run()"
```

## 四、跑完后怎么读结果

日志在 `temp\round_<标签>_<时间戳>.out`。

关键行：

```
📊 实验[detect] 局N 存活XXXs 商店N次 走位[hybrid]     ← 每局结果
补判结算页(通关/失败) conf=0.98                        ← R6 生效（正常，不是错误）
异常脱出: ...                                          ← 严重问题，需查
```

注意：`补判结算页` 是**好事**，表示正确识别了结算页。
`异常脱出` 才是问题。

**重要**：日志用 Tee 写时每行会重复两次（stdout+stderr），
统计时要先去重，否则局数会算成两倍。

## 六、两个必须知道的结论

### 1. 7b 的 5.00 不可复现

T2 用 **sha1 完全一致的 7b 原版 + 同样的 hybrid**，只跑出 3.20。

7b 全部 12 局：均店 4.25、标准差 2.77、**变异系数 65%**、
达标率 50%、区间 **0–8 店**。

**5.00 是一次运气偏好的采样，真实期望值约 4.25。**
不要用 5.00 当基线。

### 2. 核心问题是稳定性，不是均值

所有版本变异系数都在 50–100%，一半以上的局到不了 5 店。

物理约束：**shops ≈ 存活秒数 ÷ 100**，5 店需要 ≈ 600s 存活。

| 7b 历史 | 582s ← 唯一接近 600s 的 |
| 7b 今日 | 354s |
| 7b+R6 | 404s |
| 当前代码 R5 | 411s |

**问题归结为：为什么现在打不到 600s。**

## 七、待排查的疑点

### 疑点 1（P0，优先）：游戏是否变难了

游戏数据目录 `com.shenlan.m.reverse1999` 在 **11-22 01:57** 有写入，
与历史 7b 测试（11-20）隔了两天。

不能排除游戏内数值/活动变化导致难度上升。**这是最该优先排除的变量。**

**怎么查**：
- 看游戏内是否有活动/版本更新公告
- 对比历史 7b 日志（11-20）与 T2（11-22）的**同一关卡死亡时间分布**
- 若确认难度上调，则所有历史基线作废，需重新建立

### 疑点 2（P1）：局时长分布异常集中

T3 前四局存活 356 / 370 / 388 / 392s，全挤在 370s 附近。
不像自然死亡分布，像有个系统性瓶颈。

**怎么查**：统计全部局的存活时间直方图，看是否有硬性上限；
对照 `关卡` / `boss` 推进记录，确认卡在哪一层。

### 疑点 3（P2）：Boss 推进深度

历史 7b 日志有 **153 次 boss2** 记录，T1 只有 **0 次**。
长局都经历过 boss2，短局在 boss1 之前就死了。

**怎么查**：在日志里按局统计 `boss1` / `boss2` / `boss3` 出现次数，
与存活时长做相关性分析，确认 boss 阶段是否是死亡集中点。

### 疑点 4（低优先）：classify 耗时

场景分类每帧约 296–313ms，占单步约 42%。
理论上可加短期场景缓存优化，但**已被证伪不是主因**（见"三个已确定的事实"）。
