## 二、问题 A（致命）：ADB D-pad 静默丢步

### 代码

`r1999.py:1929-1948`：

```python
ax, ay = int(geom[d][0] - 5), int(geom[d][1] - 54)
try:
    if adb_tap(ax, ay):
        time.sleep(0.12)
        log(f"  ADB D-pad {d.upper()} @ ({ax},{ay})")
        return True          # ← 只要 adb 命令 rc==0 就认为成功
except Exception as e:
    log(f"  ADB D-pad {d.upper()} 异常: {e}")
```

`adb_tap`（`r1999.py:178-181`）返回 `rc == 0`，含义是 **adb 进程正常退出**，
不是 **游戏接受了这次点击**。而 `_move_one`（`r1999.py:1950-1971`）拿到
`True` 后立刻推进虚拟坐标：

```python
ok = self._press_dpad(d, self.dpad_geom)
if not ok:
    return False             # 只有 False 才不推进
delta = {...}[d]
self.last_pc = (nx, ny)      # ← 无条件推进
```

注释写着「实测 GUI 窗口/焦点切换后，桌面鼠标点击会连续多回合落不到 D-pad」，
这个观察本身是对的，但**换用 ADB 后新增了另一类失败**：ADB 点击能发出去，
游戏却因为帧时序/触点被吞而没换格。这时 `rc==0` 依然成立，日志依然打印
`ADB D-pad X`，虚拟坐标依然前进 —— **日志里看不出任何异常**。

### 实测证据

| 指标 | 5a（P15，ADB） | 7b（P13，鼠标） | 比值 |
|---|---|---|---|
| 移动指令次数 | 1,313 | 4,999 | 26% |
| ADB D-pad 日志 | 1,435 | 0 | — |
| 鼠标 D-pad 日志 | 0 | 5,625 | — |
| 视觉重定位（虚拟≠屏幕） | 871 | 3,222 | 27% |
| 战斗坐标更新（真实换格） | 640 | 2,585 | 25% |
| 平均存活 | 266s | 582s | 46% |
| 商店/局 | 2.0 | 5.0 | 40% |

「战斗坐标更新」只在 `(pi,pj)` 变化时打印，而虚拟坐标由 `_move_one` 推进；
它与「移动指令」的比例在两版接近（640/1313=49%，2585/4999=52%），说明
**决策层行为没变差，是单位时间内的有效动作数少了一半**。

### 每帧耗时拆解

| 阶段 | 5a | 7b | 差 |
|---|---|---|---|
| 检测 | 17ms | 15ms | +2 |
| 取样 | 128ms | 97ms | +31 |
| 决策 | 45ms | 31ms | +14 |
| **按键** | **282ms** | **180ms** | **+102** |
| 合计 | 473ms | 323ms | +150 |

按键环节多出的 102ms 正是 `adb_tap` 的子进程开销（`_run_cmd` 每 30ms 轮询 +
`p.communicate()`）。加上 `time.sleep(0.12)`，每步比 P13 慢约 46%，而游戏
回合是**真实时间驱动**的：帧变慢 = 同样 60 秒内少躲几次 = 更早死。

### 修复建议

1. **最小改动（推荐先做）**：把 `_press_dpad` 的首选改回桌面鼠标，ADB 作为
   回退；即交换两个分支的顺序。P13 的 5.00 就是鼠标路径跑出来的。
2. **要保留 ADB 的话**：必须让 `_move_one` 真正验证换格 —— 按完后抓一次
   小 ROI（只看玩家黄括号附近 120×120），确认 `_screen_player_cell` 变了
   才推进虚拟坐标；没变则重试一次，仍失败则回退鼠标。
3. 无论哪条路，都应把 `adb_tap` 的返回值语义改成「命令发出」而不是
   「操作成功」，避免再次误用。

## 三、问题 B（高）：屏幕坐标与虚拟坐标混用

### 代码

`r1999.py:2174-2187`：

```python
live_danger = danger                      # ← 屏幕坐标（格中心从 GRID_X0/Y0 算）
player_in_danger = (pi, pj) in live_danger  # ← (pi,pj) 是虚拟坐标
live_danger.discard((pi, pj))               # ← 用虚拟坐标删屏幕格
danger_for_screen = set(live_danger)
danger_for_screen.discard(spc)              # ← 这里才是对的
```

`in_live = player_in_danger`（`r1999.py:2446`）随后驱动逃逸承诺、
`near_danger`、边缘护栏的全部判断。

### 实测影响

从日志统计「玩家格(x,y)」与「屏幕格(a,b)」不一致的帧：

| 日志 | 总帧 | 一致 | 漂移率 | 漂移中位 | 漂移最大 |
|---|---|---|---|---|---|
| 5a | 1,313 | 1,246 | 5.1% | 1 格 | 4 格 |
| 7i | 3,426 | 3,288 | 4.0% | 1 格 | 8 格 |
| 7 | 3,551 | 3,288 | 7.4% | 1 格 | 7 格 |

漂移率 4–7%，不算高，但**最大 8 格**意味着个别帧的 `in_live` 完全错判：
玩家实际站在红区里却以为安全（不逃），或反之。

### 修复建议

`live_danger` 全程只服务屏幕坐标，应改为：

```python
player_in_danger = bool(spc_detected and spc in live_danger)
live_danger.discard(spc)
```

`(pi,pj)` 只用于虚拟世界的 BFS / Boss 距离，不再碰 `live_danger`。

## 四、问题 C（高）：`battle_step` 结构性失控

| 指标 | 数值 |
|---|---|
| 行数 | **1,034**（1973–3006） |
| `if`/`elif` | 171 |
| `else` | 28 |
| `for` | 30 |
| `log()` 调用 | 67 |
| 注释行 | 206 |
| `move_dirs` 赋值点 | **27** |
| `self.escape_commit` 赋值 | 11 |
| `self.momentum` 赋值 | 8 |
| 最大嵌套 | 11 层 |

27 处 `move_dirs = ...` 意味着**任意两处之间的覆盖关系都需要人脑推演**。
当前实际生效的优先级（按代码顺序）是：

1. Boss1 环带 / Boss2 动态禁区 / Boss3 冰带
2. `escape_commit`（逃逸承诺）
3. `momentum`（惯性）
4. 脚下/附近红区 BFS 逃逸
5. 邻格危险规避
6. 常规 hybrid/strafe/random 走位
7. 边缘护栏（**仅在 `not escape_commit and not momentum and not in_live
   and not near2 and not near_danger` 时生效**）
8. 空路径兜底
9. 屏幕红区安全层（**最后覆盖一切**）

问题在于：第 7 层护栏被 4/5/6 的产物全部屏蔽，而第 9 层又无条件清空
`escape_commit` 和 `momentum`。这解释了文档里「边缘护栏被绕过」的观察 ——
不是护栏逻辑错，而是它排在所有逃逸分支**之后**，且前置条件过严。

### 建议

不是立刻重构（风险太高），而是先做两件低风险的事：

1. 把 9 个决策层各自抽成返回 `Optional[dir]` 的私有方法，`battle_step`
   只保留一条显式的 `for layer in LAYERS: d = layer(...); if d: break`。
   行为可逐层对照验证，改动可分批。
2. 在 DIAG 里加一行「本帧方向最终由第 N 层决定」，让覆盖关系在日志里
   可观测 —— 否则任何优先级调整都无法验证。

## 五、问题 D（中）：屏幕红区闩锁退化为死代码

P13 → P15 的 diff：

```diff
-                    self.screen_exit_left = 3 if screen_in_red else 2
-                    # 当前循环约 3.3s/步，闩锁有效期必须覆盖 3 步
+                    self.screen_exit_left = 1
```

配合下面必然执行的 `self.screen_exit_left -= 1`（`r1999.py:2950`），
每次都是 `1 → 0`。下一帧 `self.screen_exit_left > 0` 恒为假，于是
`r1999.py:2910` 的整个「沿用旧方向」分支**永远不会进入**，
`r1999.py:2945` 的 `log("屏幕红区闩锁继续 ...")` 也永远打不出来。

也就是说 P15 声称「不再锁 2–3 步，避免短轴正确方向被旧方向按住」，
实际效果是**把闩锁机制整个废掉了**，而注释仍描述着已被删除的行为。

### 建议

若确认要走「每帧重算」路线，应删除 `screen_exit_dir/left/until` 三个字段
和相关分支，不要留下不可达代码；若闩锁仍有价值（P13 靠它拿到 5.00），
应恢复 `3 if screen_in_red else 2`。

## 六、问题 E（中）：红区阈值实测 —— 修正文档假设

文档假设「白格被误判成红区导致红区面积虚高」。用 5a 第 5 局 12 帧死前录像
实测（复现 `r1999.py:2096-2134` 逻辑）：

| 帧 | 当前阈值命中 | 严格阈值 | 白主导格 | 白格被误判 |
|---|---|---|---|---|
| f00 | 40 | 0 | 0 | 0 |
| f02 | 24 | 1 | 9 | 0 |
| f03 | 49 | 0 | 0 | 0 |
| **f05** | **65** | **17** | 39 | **3** |
| f09 | 53 | 0 | 0 | 0 |
| f11 | 8 | 0 | 42 | 2 |

f05 命中 65 格，正是日志里记录过的峰值。逐格颜色分布：

- `r-g > 40`：**48 格**（真暗红，R≈113–195，G≈51–101）
- `r-g` 在 20–40：17 格（棕/粉，多为棋盘边框与地板）
- 白格被误判：**仅 3 格**

**结论：主因不是白格，而是松散阈值 `(r > 80 and r-g > 20 and r-b > 20)`
把整片暗红（48 格）全部并入 `danger`。** 这 48 格本身是真实危险区，问题在于：

1. 它们全部进入 `live_danger` → `near2` 大面积成立 → 逃逸分支持续抢占
   走位，常规清怪被饿死（商店进不去）。
2. `>80 格整帧丢弃` 的兜底线太高：5a 触发 0 次，7b 触发 29 次 —— 说明
   这条兜底在 P15 的样本里根本没起作用。

### 建议

- 把松散分支的 `r-g > 20` 提到 `> 35`，可直接滤掉 17 格棕/粉（保留 48 格真红）。
- 区分「红区面积」与「是否该逃」：面积 > 30 格时不应整片逃逸，而应只逃
  玩家所在连通块的外接框（现在 `_box_containing` 已经这么做，但 `near2`
  用的是全局 `live_danger`，需要改成只对玩家所在块生效）。
