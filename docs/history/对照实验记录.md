# 对照实验：走位模式 vs 代码版本

测试时间：2026-11-21 10:52 — 12:20
目的：分离「代码差异」与「走位模式差异」，判定五轮测试结论是否有效

---

## 一、发现的问题（我的测试设计失误）

五轮测试（R0–R5）全部通过 `temp\_run_round.py` 以命令行方式启动，
该脚本未设置 `R1999_NO_DANGER_MODE`，于是落到代码兜底值 **`strafe`**。

而历史版本 5a/7/7b/7h/7i 全部通过 GUI 启动，`gui.py` 里该选项默认
**`hybrid`**：

```python
# gui.py
self.r1999_mode_var = tk.StringVar(value="hybrid")
# main.py（命令行）
choices=("strafe", "random", "hybrid"), default="strafe"
```

**后果**：五轮数据是「改了代码 + 换了走位模式」的双变量实验，
与 7b 的 5.00 不可比。这解释了此前想不通的矛盾——R3 已把红区与
选卡全部回退到 P13 状态，均店却仍是 3.43 而非 5.00。

## 三、结论

### 1. 走位模式的影响被确认，但只在 7b 上成立

**7b 换模式：5.00 → 3.20（−1.80 店）**，这是干净的 A/B 对照
（同一份代码、同一个脚本、只改环境变量），差异显著。

但**当前代码换模式：3.14 → 2.75（−0.39 店）**，方向相反且幅度小，
在 4 局样本的噪声范围内（当前代码 strafe 的逐局标准差就有 1.95）。

**这说明：hybrid 不是普适的提升项，它与 7b 的代码实现存在耦合。**
当前代码在 R1/R5 改动了逃逸与结算逻辑，可能已经改变了 hybrid
所依赖的行为前提（例如 hybrid 的「周期冲刺」依赖逃逸不被频繁打断）。

### 2. 五轮测试的绝对数值仍然有效

R1–R5 全部在同一走位模式（strafe）下进行，**轮次之间可以互相比较**：

| 轮次 | 均店 | 判定 |
|---|---|---|
| R1 | 3.43 | WIN 修复有效 |
| R2 | 2.14 | 选卡颜色负向 |
| R3 | 3.43 | 回退选卡有效 |
| R4 | 2.57 | 半分辨率负向 |
| R5 | 3.14 | 怪格降级有效 |

这些相对结论不受走位模式影响。失效的只是「与 7b 的跨版本对比」。

### 3. 7b 的 5.00 需要谨慎看待

7 局样本、变异系数 49%、有一局 0 店。达标率 71% 看似很高，
但 5 局样本下 5.00 与 3.20 的差异并不具备统计显著性
（Mann-Whitney U 检验 p ≈ 0.15）。**7b 的 5.00 至少部分是运气。**

## 四、R6 修复：WIN 结算页漏判（本轮附带发现并修复）

### 问题

实验 B 第一次运行时，局 1 跑出 266s / 3 店后**异常脱出停机**。
存证图 `temp/r1999_escape_115500.png` 显示那是一张 **WIN 通关页**
（通关数量 12、击杀 1352、最高评价 **S**）——一次极成功的超长局被丢弃。

### 根因（两个缺陷叠加）

用该截图离线分析：

| 场景模板 | 得分 | 阈值 | 结果 |
|---|---|---|---|
| shop | **0.7510** | 0.72 | ★ 命中 |
| entry | 0.4887 | 0.72 | |
| battle | 0.4385 | 0.68 | |
| gameover | 0.3888 | 0.72 | |

WIN 页被 `classify` 判成 **`shop`**（右侧金色奖杯/按钮区与商店模板相似），
而不是 `unrecognized`。

而 R1 修复的补判代码条件是：

```python
if scene == "unrecognized" and not self.has_dpad(img):
```

**条件被 `scene == "unrecognized"` 锁死，补判从未执行。**
R1 的 0.78 阈值本身是对的（`gameover_stats` 实测 0.7956 > 0.78），
但它没机会运行。

### 修复

判据改为「无十字键」本身：

```python
if not self.has_dpad(img):
```

依据：**R5 的 3475 个战斗帧中，十字键缺失告警 0 次**——该特征极可靠。
结算页才是唯一「无十字键」的正常界面。

### 验证

| 画面 | dpad | gameover | stats | 补判结果 | 正确 |
|---|---|---|---|---|---|
| WIN 结算页 | False | 0.3377 | **0.7956** | gameover | ✓ |
| 商店页 ×4 | False | 0.33–0.41 | 0.50–0.60 | 保持原场景 | ✓ |
| 战斗帧 | **True** | 0.3345 | 0.6858 | 不进入补判 | ✓ |

余量：WIN 0.7956 与商店最高 0.6049 之间相差 **0.19**，区分充分。

实机复验（`temp/_now.png`）：stats **0.8808** → 正确判为 gameover。

运行效果：B2 中补判触发 **10 次**，全部正确，**异常脱出 0 次**。

## 五、下一步建议

1. **保留 R6 修复**（无争议，纯收益：不再丢通关局）。
2. **走位模式不要贸然切到 hybrid**——在当前代码上它是负向的（3.14→2.75）。
3. **若要复现 7b 的 5.00，应整体回退到 7b 代码 + hybrid**，而不是在当前
   代码上切模式。但这意味着放弃 R6/R5 的修复。
4. **更值得做的**：把 R6 修复单独移植到 7b 代码上，用 hybrid 跑 7 局，
   看能否在保住 5.00 的同时消除丢局。这是唯一能同时拿到「高均值」和
   「不丢局」的路径。
