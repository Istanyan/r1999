## 0. 一句话架构

**一个通用的「截图 → 识别 → 决策 → 输入」引擎（core/）+ 多个游戏插件（games/）+ 两套入口（CLI main.py / GUI gui.py）。**

引擎完全不含游戏逻辑；所有游戏差异都在 `GameScript` 子类里。唯一的例外是 r1999——它基本绕开了引擎，自管一个 3000 行的实时循环。

## 2. 数据流（一次完整执行）

### 2.1 CLI 路径

```
main.py::main()
  → check_my_lock()                    单实例锁（心跳 5s 刷新，15s 过期）
  → GameBot(window_title, game_name)   构造截图/匹配/OCR/输入四件套
  → run_game(bot, script)
      → script.startup(bot)            启动清理（签到/关公告/回主界面）
      → execute_tasks(bot, tasks)      任务引擎主循环
          → register_task_thread()     把当前线程标记为可急停
          → for loop in range(50):
              先跑所有 repeat=True 任务（检查 cooldown）
              再跑所有 repeat=False 且未 done 的任务
              → task.callback(bot) 或 bot.click_if_found(task.template)
              → 成功则 task.done=True
              → 失败累计 3 次则跳过
              → after_task 钩子（三国杀用它插入演武检测）
```

### 2.2 GUI 路径

```
gui.py::_start()
  → 重置一次性任务 done / 清空日志
  → threading.Thread(target=_run_script)
      → register_task_thread()
      → 按 game 名调整 window_title（bbdc→"MuMu安卓设备"，deltaforce→None）
      → _apply_r1999_env()  读界面控件 → 写 R1999_MAX_RUNS 等环境变量
      → GameBot(...)
      → _inject_interruptible_sleep(bot)   替换 bot.sleep
      → run_game(bot, script, tasks=self.tasks, stop_flag=self.stop_flag)
```

GUI 与 CLI 走**同一个 `run_game`/`execute_tasks`**，差异只在参数注入和状态回传。

### 2.3 r1999 的独立数据流（重要）

```
R1999Script.get_tasks() → [Task("街机挂机", repeat=True, callback=_run_loop)]
    ↓ 引擎每次调度都调一次
_run_loop(bot)
    → Loop()                 ← 每次新建，全新状态
    → Loop.run()             ← 315 行主循环，最长 MAX_RUNTIME=3h
        → cap()              截图（桌面快速帧优先，失败回退 ADB）
        → classify(img)      11 个场景模板取最高分
        → 按场景 dispatch:
            battle    → battle_step(img)     ← 1032 行，核心
            shop      → handle_shop(img)
            blessing  → handle_blessing(img)
            hub       → handle_hub()
            gameover  → 记账 + 死前录像落盘 + 点空白
            title/mainui/warning/pause/reward → 恢复链
            unrecognized → handle_unrecognized()
    → 结束后：stop_reason ∈ {max_runs, score_target, escape, danger, space}
      则抛 StopRequested，让引擎在同一轮收尾；否则 return True 被 repeat 再次拉起
```

**`repeat=True` + 内部 3h 上限 = 整夜挂机。** 这是设计意图，不是 bug。

## 3. 引擎层逐模块要点

### 3.1 core/screenshot.py
- `find_window_rect(keyword)`：枚举可见窗口，按标题子串匹配，返回 `(rect, hwnd)`。
- `raise_to_foreground(hwnd)`：绕过 Windows 前台锁的三板斧——模拟按 ALT 解除前台锁 → `AttachThreadInput` 共享输入权限 → `TOPMOST/NOTOPMOST` 兜底 z 序。
- `Screenshot.capture()`：mss 截取窗口矩形 → 返回 BGR ndarray。
- `sync_window_rect()`：每次截图前同步窗口位置（用户拖动窗口后偏移量会变）。

**坑**：截图区域 = 窗口矩形，包含标题栏和工具栏。MuMu 主窗 1930×1139 里有 5px 左边框 + 54px 顶栏，所以 ADB 坐标 = mss 坐标 − (5, 54)。

### 3.2 core/matcher.py
- `_imread()`：用 `np.frombuffer + cv2.imdecode` 绕开 cv2.imread 不支持中文路径。
- `match_one`：`TM_CCOEFF_NORMED` 全图匹配取最大值，返回中心坐标。
- `match_one_gray`：转灰度再匹配，忽略颜色（应对皮肤/底色变化）。
- `match_all`：取所有 ≥ 阈值的位置 + 简单 NMS 去重。

### 3.3 core/ocr.py
- PaddleOCR 懒加载（`ocr` property）。
- `_redirect_home_if_needed()`：**中文用户名会导致 Paddle C++ 引擎打不开模型**（`C:\Users\言\` 非 ASCII），临时把 `USERPROFILE` 重定向到项目下的 `paddle_home/`。
- 导入 paddleocr 会篡改 root logger 级别，代码在导入前后保存/恢复 `root_logger.level`。

### 3.4 core/action.py（最需要注意的文件）
- `pyautogui.FAILSAFE = True`，`PAUSE = 0`（0.1s 的 pause 会毁掉蛋糕小游戏精度）。
- 空格急停双通道：`keyboard` hook + `GetAsyncKeyState` 轮询（后者带前台门控，只在 MuMu 在前台时生效）。
- watchdog 线程：注入 `StopRequested` 到任务线程 → 3s 不退出就强杀进程。
- **`time.sleep = _interruptible_sleep`（第 316 行）——全局 monkeypatch。**
  任何模块里的 `time.sleep` 都被替换成 50ms 分片检查停止标志的版本。这是急停能在整个项目生效的机制，但也是隐式全局副作用，重构时不能随便去掉。

### 3.5 core/instance_lock.py
心跳锁而非 PID 锁。原因写得很清楚：Windows PID 复用会导致残留锁被误判为"实例在跑"，两个 bot 互抢鼠标。

## 5. r1999 深度解剖

### 5.1 坐标系（必须牢记）

| 系统 | 分辨率 | 原点 |
|---|---|---|
| mss 画布 | 1930×1139 | MuMu 主窗口矩形左上角 |
| ADB | 1920×1080 | 模拟器屏幕左上角 |
| 换算 | `adb = mss − (5, 54)` | 实测 1:1 无缩放 |

`_desktop_frame()` 把 1920×1080 的渲染窗画面贴到 1930×1139 画布的 `[54:1134, 5:1925]`，正是为了让两套坐标统一到 mss 画布。

`render_click_point(x, y)`：mss 画布 → 渲染窗客户区屏幕坐标，按客户区实际尺寸做比例换算（应对窗口缩放）。

### 5.2 棋盘几何

```
GRID_N = 15
CELL_W = 60.3   CELL_H = 60.0
GRID_X0 = 515   GRID_Y0 = 145
cell_center(i,j) = (515 + (i+0.5)*60.3, 145 + (j+0.5)*60.0)
```

15×15 = 225 格，棋盘区约 905×900 px。

### 5.3 场景分类

11 个场景：`gameover, battle, entry, blessing, shop, hub, warning, title, pause, mainui, reward`

`classify()` 把图缩到半分辨率，对 11 个模板逐一 `TM_CCOEFF_NORMED` 取最高分，低于该场景阈值（battle 0.68 / mainui 0.75 / 其他 0.72）则判 `unrecognized`。

**注意：`Loop.__init__` 里对 11 个场景模板和 6 个按钮模板都有 `assert t is not None`。少任何一张 PNG，实例化直接崩。这是 SCENES=11 必须保住的原因。**

### 5.4 battle_step 的真实结构（修正版）

这是全项目最复杂的函数：**L1973–3004，1032 行**。

实测结构（AST 分析）：

| 指标 | 数值 |
|---|---|
| 顶层语句 | 125 个 |
| If 节点总数（含 elif） | 159 |
| For 循环 | 25 |
| 函数调用 | 350 |
| `log()` 调用 | 67 |
| 真实最大缩进 | 46 空格 ≈ **11 层**（L2887） |
| 顶层 if/elif 链根节点 | 37 个 |
| `move_dirs`/`escape_commit`/`momentum`/`screen_exit_left` 赋值次数 | 27 |

**关键修正**：那条看似 12 层深的 `if boss_mode … elif is_boss3 … elif self.escape_commit …` 链，**实际上全部是 8 空格缩进（同一层）**，是一个 37 分支的平铺决策表，不是深层嵌套。真正的 11 层缩进只出现在 L2887 附近的局部表达式里。

这对重构意义重大：**它是"一个巨大的平铺决策表"，不是"俄罗斯套娃"**。重构方向应该是把 37 个分支抽成有序的决策规则列表（strategy list），而不是拆嵌套。

### 5.5 battle_step 的 6 个逻辑阶段

```
① 进场守卫  L1976-1982   首次进入等 3.2s 动画 + 抢键盘焦点
② 感知      L1983-2061   截图 → 找玩家屏幕格 → 视觉重定位虚拟坐标
③ 危险识别  L2062-2216   白环 / 红区 / 白怪 / 记忆 / BFS 障碍集
④ 目标识别  L2217-2439   占位格 / 出口 / 模板怪 / 边怪 / boss
⑤ 决策      L2440-2950   37 分支平铺决策表 → move_dirs
⑥ 执行      L2951-3004   按 move_dirs 逐个按 D-pad + 节拍控制
```

### 5.6 决策优先级（⑤ 阶段实际顺序）

```
1. boss_mode 且玩家不在危险中          → Boss1 环带走位
2. is_boss3                            → 冰地/三段走位
3. escape_commit                       → 已承诺的逃逸方向（跨帧锁）
4. momentum                            → 逃逸惯性（顺势多跑几格）
5. in_live 或 near2（玩家在危险/危险逼近）→ 逃逸 BFS
6. near_danger                         → 邻近危险规避
7. white_soft                          → 白怪软代价规避
8. not mobs 且 exit_target             → 清场出口（最外圈粉箭头）
9. self._edge_target                   → 边怪追击（贴身攻击，3 次不消失则拉黑）
10. 贴边（离边≤3）                     → 强制回中
11. momentum（第二处，重复判断）
12. off_center > CENTER_RADIUS(6)      → 回中心
13. not boss_mode                      → 默认 strafe 左右交叉 / random 对照
14. 兜底                               → _pick_strafe
```

**问题：第 4 和第 11 都是 `elif self.momentum`，第 11 处永远不可达**（第 4 处若 momentum 为真就会命中，为假则第 11 处也为假）。这是死分支。

### 5.7 D-pad 输入（P15 回归的根因所在）

`_press_dpad(d)` 当前逻辑：

```python
# L1933-1940  优先 ADB
ax, ay = int(geom[d][0] - 5), int(geom[d][1] - 54)
if adb_tap(ax, ay):
    time.sleep(0.12)
    log(f"  ADB D-pad {d.upper()} @ ({ax},{ay})")
    return True
# L1941-1948  回退鼠标
if not self._input_focused:
    self._input_focused = self.focus_game_input()
    interruptible_sleep(0.30)
sx, sy = self.render_click_point(*geom[d])
pyautogui.click(sx, sy)
```

**`adb_tap` 返回 `rc == 0`，含义是"adb 命令执行成功"，不是"游戏接受了这次点击"。**

`_move_one` 拿到 `ok=True` 就无条件推进虚拟坐标：
```python
ok = self._press_dpad(d, self.dpad_geom)
if not ok: ... return False
self.last_pc = (nx, ny)      # ← 无条件推进
```

于是 adb 点击被游戏吞掉时，虚拟坐标照常前进，**日志里看不出任何异常**——这是 P15 从 5.00 掉到 2.0 店/轮的完整机理。

### 5.8 红区识别（`red_cells` 生成，L2096-2134）

```python
if (r > 155 and r - g > 60 and r - b > 60) or \
        (r > 80 and r - g > 20 and r - b > 20):
    red_cells.add((i, j))
```

- 第一支：亮红爆炸区（原判定）
- 第二支：暗红倒计时格（新增，阈值很松）
- 然后连通块 ≥4 才并入 `red_zone`
- `len(red_zone) > 80` 整帧丢弃（防棕色地板）

**实测问题**：第二支的 `r-g > 20` 会把约 17 个棕/粉色棋盘边框格吸进来。在 5a 的 12 帧死亡样本里，f05 命中 65 格，其中 48 格是真实暗红（r-g>40），只有 3 格是白色误读。**所以"白格误判成红区"这个流传的说法基本不成立，真实原因是阈值太松放进了边框。**

### 5.9 死前录像机制（已确认存在）

| 位置 | 作用 |
|---|---|
| L481 | `self._frame_buf = deque(maxlen=12)` |
| L1985 | `battle_step` 每帧 `append((t0, img))` |
| L2033 | 每场战斗开始 `clear()` |
| L3396-3408 | GAME OVER 时落盘 `temp/r1999_death_HHMMSS/f{i:02d}_{t:.1f}.jpg`，JPG q85 |

每局产出 12 帧 × 约 320 KB ≈ 3.8 MB。归档里 196 个目录共 703 MB。

### 5.10 状态变量清单（重构时必须一起处理）

`Loop.__init__` 初始化了 **80+ 个实例属性**，其中与决策强相关的：

## 7. 重构路线（基于本次通读）

### 优先级 1：恢复鼠标优先（修 P15 回归）
改 `_press_dpad`：鼠标优先，ADB 仅在窗口非前台时兜底。
**不要**只改顺序——还要让 `_move_one` 在"按了但画面没变化"时不推进坐标（当前完全没有这个校验）。

### 优先级 2：决策表抽成规则列表
`battle_step` 的 37 个平铺分支可以改写成：
```python
RULES = [
    ("boss_ring",      lambda s: s.boss_mode and not s.in_live,  _boss_ring),
    ("boss3_ice",      lambda s: s.is_boss3,                     _boss3),
    ("escape_commit",  lambda s: s.escape_commit,                _commit),
    ...
]
for name, cond, handler in RULES:
    if cond(state):
        dirs = handler(state)
        if dirs: break
```
这样能顺带发现死分支（momentum 重复）、能单测每条规则、能加日志看哪条规则命中。

### 优先级 3：把 80 个属性收进状态对象
`BattleState` dataclass 承载坐标/逃逸/目标/Boss 状态，`battle_step` 只做感知→更新 state→查规则→执行。这是让 1032 行变成可维护代码的唯一路径。

### 优先级 4：`save_evidence` 改滚动覆盖
当前每次商店进/刷新/买都存一张 1.8 MB 全屏 PNG，5 局测试就产生 6.4 GB。改成同 tag 覆盖 + JPG q85，体积降到 1/5 以下。

## 9. 项目现状总评

**做得好的地方：**
- 引擎与游戏解耦得很干净，`core/` 1155 行没有任何游戏特定代码。
- 常量集中管理，且带实测标定历程（蛋糕的调参注释、boss 血条的 24 帧离线验证）。
- 急停机制做到位了：全局 sleep 接管 + watchdog 强杀，能应付 OCR/C 调用卡死。
- 对"绝不误点"有很强的意识：危险页门禁、主界面/标题出现即停止、只点取消不点确定。
- 踩过的坑都留了注释，且写明日期和现象（如 cv2.imread 读错内容、中文用户名 OCR 失败、PID 复用）。

**需要改的地方：**
- `battle_step` 1032 行 37 分支，是唯一无法维护的函数。
- 80 个散落状态属性，没有封装。
- `_move_one` 无条件推进坐标，掩盖输入丢失（P15 回归根因）。
- `save_evidence` 无节制写全屏 PNG。
- 死分支：`momentum` 判断重复、`screen_exit_left=1` 后立即自减导致闩锁分支不可达。
- 项目无 git，历史靠手工快照目录。
